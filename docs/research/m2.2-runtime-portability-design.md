# M2.2 runtime and installation portability — Stage A

Status: **Stage A accepted with CONDITIONAL GO. B1 feasibility authorized; B2 requires separate approval.**
The review approved Windows npm-runtime isolation in principle and conditionally
approved a small native bootstrap, subject to executed feasibility evidence.
The original Stage A analysis below described these two requested exceptions:

1. Permit a narrowly scoped correction to Windows npm-script runtime selection in
   `src/process.ts`. The existing implementation explicitly uses Arch's Node for
   npm-backed native commands. Keeping that implementation unchanged conflicts
   with running Arch on Node 24 while the project/native command uses Node 20/22.
2. Permit a small Windows native bootstrap, retaining the existing route `.exe`
   and `.shim`. A Node-independent runtime resolver cannot itself require Node.
   Its console, quoting, cancellation and packaging feasibility must pass a
   prototype gate before production integration. If it fails, return for review;
   do not substitute PowerShell, cmd, a bundled runtime or a framework silently.

The implementation checkpoint is split: B1 proves executable runtime/console
behavior and corrects npm Node selection; B2 covers installation, migration and
real version-manager tests only after B1 approval. See
[B1 results](../m2.2-b1-feasibility-report.md). PATH-only resolution remains an
insufficient complete solution for projects using Node 20/22.

## Root causes and the three runtimes

`renderFiles()` embeds `process.execPath` and its own absolute `cli.js` location.
Repeated init deliberately trusts historical file hashes; reconciliation retains
existing routes byte-for-byte. Neither operation rebinds old launchers today.

`inspectInstallation()` and removal validate manifest paths and bytes, not the
continued existence of captured executables. This is correct: availability and
ownership are different properties. Preserve this separation.

`process.ts` already removes marked router directories from native PATH and
rejects recursive realpath targets. However, its Windows npm `.cmd` handling
reads the script target and launches it with `process.execPath`. That makes the
native CLI's runtime equal to the harness runtime regardless of the project.
This conflicts with M2.2 isolation even if the new bootstrap never alters PATH.

The intended separation is:

| Runtime | Selection authority | Must not affect |
| --- | --- | --- |
| Arch | Explicit Arch override, then incoming PATH, validated against engine range | Project configuration, native PATH/Node selection |
| Project | User's shell/version manager/project configuration | Arch's compatibility requirement |
| Native CLI | Native executable/shebang/npm-shim semantics using incoming native environment | Arch installation/runtime policy |

There is no automatic runtime acquisition. Missing compatible Arch Node is a
diagnosed failure. The existence of Node 20/22 for the native CLI does not make
it compatible with the harness.

## Alternatives considered

| Alternative | Portability and predictability | Security/integration | Maintenance and recovery |
| --- | --- | --- | --- |
| A: PATH Node only | Removes captured Node; fails when project selects 20/22 | Familiar shell trust, no implicit version-manager operation | Cheapest; insufficient alone |
| B: implicit `mise exec node@24` | Could choose Arch runtime, but depends on mise availability/configuration | Changes environment; may install unless constrained; unsuitable as universal default | Adds manager-specific behavior and recovery; reject |
| C: stable Node copy managed by Arch | Survives removal of original executable | Requires runtime updates/security maintenance; copying a Node executable is not a complete portable runtime installation | Becomes runtime management; reject |
| D: independent bootstrap only | Can resolve compatible Node without running Arch under an old one | New executable boundary must preserve environment/console and reject recursive candidates | POSIX shell is small; Windows needs native feasibility work; does not solve checkout location |
| E: stable installation plus narrow resolver | Separates checkout, runtime and project lifecycle; explicit override handles incompatible project Node | User-owned installation, bounded lookup, no downloads/profile changes | Smallest complete candidate when combined with D; recommended conditionally |

`npm link` remains development convenience, not the stable-install solution.
It links package/executables through npm's selected global prefix. nvm documents
global-package migration between Node installations. A global prefix or its PATH
entry may change with a version switch; Arch cannot guarantee that an npm-created
link is available afterward without taking over shell/version-manager policy.
Do not configure a global npm prefix as a universal nvm workaround.

## Recommended architecture (proposed, not implemented)

### Stable, user-owned application snapshot

**Review adjustment: standard npm installation is the preferred B2 candidate.**
Before any custom installer, compare `npm pack` followed by
`npm install --global --prefix <explicit-stable-directory> <local-tarball>`.
The prefix is supplied per command, not configured globally; npm retains dependency
installation and ordinary bin linking. The tarball avoids source-checkout symlinks.
A B1 dry-run on npm 12.0.2 included built `dist/*` and `vendor/*`; no stable install
was performed. Installation/offline behavior, payload completeness, executable
placement and removal still need real B2 tests against the supported npm versions.

This standard option removes most justification for the custom copy script proposed
below. Do not implement that script unless B2 identifies a concrete contract npm
cannot meet. Keep `private: true`, publishing out of scope, and runtime resolution
separate: standard npm shims alone still require ambient Node. No automatic PATH or
profile edits. The following snapshot description records the original alternative,
not authorization to build a custom installer.

Retain npm bin and `npm link`. Add an explicit, noninteractive local installation
script (`npm run install:stable -- --destination <absolute-directory>`), separate
from `init`. Require the destination; do not derive it from a project's HOME or
configuration. Copy only built application files, package metadata, production
dependencies and vendor/bootstrap artifacts from a bootstrapped checkout. No
registry publishing, downloads, runtime copying, package manager, auto-updater or
background service. Reuse standard npm packaging/file-list facilities to define
the payload; prove it contains all runtime dependencies offline.

Proposed layout:

```text
<destination>/bin/arch          # POSIX native shell bootstrap
<destination>/bin/arch.exe      # Windows native bootstrap
<destination>/app/dist/cli.js
<destination>/app/node_modules/...
<destination>/app/vendor/...
```

The public installer refuses an occupied destination. No in-place upgrade
transaction framework: install a new snapshot beside the old one, validate it,
then explicitly rebind projects. Keep the old installation until users no longer
need it. For recovery, invoking a different intact installation is sufficient.
Removing a stable snapshot is an explicit user operation; it never deinitializes
projects. Installation must not write to target projects, shell profiles or PATH.

Users can choose an already-PATH-visible user bin directory for the executable,
or invoke its absolute path. If no suitable directory is on PATH, bare `arch`
availability necessarily needs a user shell/PATH decision; do not claim otherwise
or edit profiles automatically. Document a manual setup step and full-path use.
A stable snapshot is independent of the source checkout but not invulnerable to
deletion of its own directory.

This explicit snapshot script is a local file-copy operation, not package
distribution or a runtime manager. If the payload cannot remain small and
self-contained, stop for review instead of adding bundling infrastructure.

### Runtime policy

Bootstrap inputs are incoming cwd, environment, arguments and its own installation
location. Proposed override: **`ARCH_NODE`**, an absolute executable file path,
with no arguments. No search of project TOML, ancestors, registry, manager caches,
or arbitrary installed versions. No persistent runtime-selection state.

1. If `ARCH_NODE` is set, validate that candidate. Invalid/missing/incompatible
   override is a hard error; do not silently fall through.
2. Otherwise resolve the first native `node` on incoming PATH, respecting platform
   executable semantics. Skip marked Arch router directories and reject aliases
   to Arch bootstrap/route executables. Do not search later PATH entries merely
   because the first Node is incompatible. Empty entries/current-directory search
   are not an implicit fallback. Document this deliberate runtime lookup boundary.
3. Probe the candidate directly with a bounded `--version` invocation, no shell,
   and validate the exact package engine range. Probe failure, timeout, unavailable
   file or incompatible version is actionable and does not execute harness code.
4. Run the harness using that candidate and the local application payload. The
   CLI also checks `process.versions.node` before dynamically importing the harness
   so direct Node and npm-bin invocations cannot bypass compatibility validation.
   Keep the check syntactically conservative; no static harness import before it.
5. Diagnostics name the source/candidate/version and required range. Explain how
   to select a compatible runtime externally and set `ARCH_NODE`, or restore PATH.
   Never print the full environment or imply Arch will install Node.

For an incompatible project Node, the user can set `ARCH_NODE` to an independently
maintained compatible Node. Switching the project version does not alter that
choice. Removing the selected override intentionally fails until the user repairs
the override; there is no magic discovery of another installation. Without the
override, replacing PATH Node 24 with another compatible installation works.

Do not prepend Arch's runtime directory to PATH. Pass incoming environment and
cwd unchanged into the harness; retain existing router-directory filtering only
at the existing native-execution boundary. Avoid environment transport of saved
PATH values, shared temp state, or per-process global selectors. Treat NODE_OPTIONS
and manager shims as user-controlled execution inputs, not a security sandbox.
Manager shims must not trigger Arch-initiated installs; test offline behavior.
Explicit executable selection is safer and more predictable for independent Node.

Version probing is a compatibility check, not attestation. A malicious PATH Node
can already run arbitrary code. Do not elevate privileges or trust unowned files.
File replacement between probe and execution is not solved by a lock/framework;
the CLI's own version guard provides a second check.

### Platform boundary

POSIX bootstrap uses a shell only for runtime lookup/validation and finishes with
`exec`, preserving arguments with `"$@"`. Do not use `eval`, unquoted expansion or
`mise exec` to start the harness. Validate version parsing, spaces, Unicode,
symlinks, executable permission failures and no-runtime diagnostics.

On Windows, retain route `command.exe` from Scoop and its `.shim`; the `.shim`
points to the stable **Arch bootstrap executable**, with fixed `run command --`
arguments. The bootstrap resolves Node, probes compatibility, then starts the
harness with inherited handles/environment/cwd and correct Windows argument
quoting. Its management `arch.exe` entry uses the same implementation. It must
not detach, create a new console, use `cmd /c`, interpolate arguments into
PowerShell, or reinterpret the native argument tail.

This adds one narrow native source/build artifact, not a second CLI. Cross-build
and artifact provenance, console Ctrl+C/Ctrl+Break, child completion, probe timeout,
exit propagation and repeated launch must pass before committing to it. Keep
x64 supported; Windows ARM64 can remain explicitly unverified. If the existing
Scoop launcher can provide the complete policy with less code, prefer that only
after source inspection and executable proof; its current use does not prove it.
Do not replace the route `.exe/.shim` mechanism to simplify bootstrap design.

The npm bin remains `dist/cli.js`; its standard npm shim first needs a runnable
ambient Node. The CLI's conservative entry guard can re-exec via valid `ARCH_NODE`
when started under a supported bootstrap-host Node 20/22, but harness modules must
never load there. A missing npm prefix/Node still requires the independent stable
bootstrap. Clearly distinguish bootstrap-host compatibility from Arch's engine;
test it rather than weakening `engines`.

### Windows native CLI isolation exception

For Node scripts behind supported npm `.cmd` shims, preserve script extraction,
argument-array execution and rejection of arbitrary batch scripts. Choose the
native Node using the shim's supported semantics (adjacent Node when the standard
shim requires it, otherwise Node on the existing filtered native PATH), **never
ARCH_NODE or Arch's process.execPath**. Do not require native Node to meet Arch's
engine range. Fail with a native-runtime diagnostic if it is unavailable.

This is a deliberate behavioral correction and requires approval. Define the
supported npm-shim subset explicitly using generated real npm shims; do not claim
general batch interpretation. Core execution API, cancellation contract, stdio,
signals, EDA and middleware interfaces remain unchanged. No PATH substitution
around a spawn: the child must see the project's original native environment.

## Launcher compatibility, migration and recovery

Keep existing M1/M2/M2.1 manifest shapes and hashes. New manifests use the same
`files`/`createdHarness` structure; launcher bytes may reference the stable
bootstrap instead of a historical Node/checkout. Never validate ownership against
today's renderer or require old executable targets to exist.

No automatic migration during status, init, configure, CLI installation or update.
Do not add a new generic transaction/rebind journal in this milestone. Existing
reconciliation retains old launchers; documenting that is mandatory.

The minimal safe explicit **rebind procedure** is:

1. Invoke a working current/stable Arch by full path with compatible Node.
2. Run `status --json` and record selected routes. Resolve pending recovery using
   recorded operations, never by executing old launchers.
3. Run `deinit --yes`; existing hashes/path checks protect changed launchers.
4. Run `init <recorded-commands...>` using the chosen stable installation.
5. Inspect status and explicitly verify routing separately from mise activation.

This is not atomic: a crash between deinit/init leaves routing absent, not silently
half-rebound. Re-run init after inspecting state. Modified user middleware survives
existing deinit rules; unchanged generated middleware may be removed/recreated.
Document that limitation before presenting rebind as a command recipe. Do not
automatically chain deinit/init after partial failure or write an invented manifest.

Old missing Node/checkout paths do not invalidate ownership. Status can add
availability warnings only for strictly recognized launcher templates, never
execute launcher content or use target reachability as deletion authority. Unknown
hash-valid legacy launchers remain removable without parsing their arguments.
Avoid required status JSON/schema changes; additive warnings are sufficient.

Recovery retains existing exclusive hard-link publication, journals and hash
validation. Deinit may first need to complete routing recovery, including hard
links; exFAT remains unsupported for that operation. Do not bypass a journal merely
because an old runtime or installation is missing. Interrupted uninstall continues
from its ownership checkpoint; repeated deinit stays idempotent. A byte-modified
managed launcher remains protected even if its target no longer exists.

## Failure modes and rejected shortcuts

| Failure | Required result |
| --- | --- |
| Compatible PATH Node replaced | Resolve new Node; no captured dependency |
| PATH Node is 20/22, valid independent ARCH_NODE | Arch uses compatible override; native CLI keeps project Node |
| PATH Node incompatible, no override | Error before harness load; no project mutation |
| Override removed or incompatible | Explicit diagnostic, no hidden fallback |
| Source checkout rebuilt/moved/deleted after stable snapshot | Snapshot/project routes unaffected |
| Stable snapshot removed | Route failure is actionable; different intact Arch can inspect/deinit |
| npm link lost with version-manager prefix | Stable entry still available by its independent path; npm link requires explicit relink if wanted |
| Legacy launcher modified | Ownership refusal; do not overwrite or delete |
| Concurrent projects with distinct Node/PATH | Per-invocation selection, no shared runtime state |
| Routing/uninstall interrupted | Existing recorded ownership/recovery remains authoritative |

Rejected: PATH-only claims of full portability; invoking `arch` by name from route
launchers; project-local runtime auto-selection; copying/downloading Node; implicit
mise runtime overrides; environment PATH mutation; PowerShell as an unproven
transparent Windows launcher; adding stable-install pointers to every manifest;
automatic launcher rewriting; custom self-update/package-distribution machinery;
generic filesystem transactions; weakened ownership checks.

## Stage B validation gates

First prove the Windows bootstrap and isolation exception on a throwaway branch.
If this cannot meet unchanged console/argument contracts, stop and request review.
Do not call architecture feasible based on unit mocks alone.

Then automate these cases with temporary installs, isolated npm prefixes/caches and
user homes. Never modify real global Node installations:

| Area | Required executed evidence | Stage A status |
| --- | --- | --- |
| Historical path failures | Copied executable removal and checkout relocation | PASS on Windows x64 only |
| Existing recovery/compatibility | Focused M1, uninstall and real lifecycle interruption tests | PASS: 25 baseline tests |
| Ownership independent of target availability | External status/deinit with missing targets | PASS on Windows x64 |
| New runtime selection and compatibility guard | Real Node 24.15+ copies, second 24, actual 20/22, missing/restored candidate, override precedence, malformed output/timeout, no harness side effects | NOT TESTED |
| Version managers | Actual offline nvm switch on POSIX; fnm or mise switch where available; distinguish manager tests from PATH simulation | NOT TESTED |
| Stable installation | Clean bootstrap/install, delete source checkout, verify complete payload; occupied-destination refusal; install beside old; no project/profile/PATH mutation | NOT TESTED |
| npm installation | Isolated link/help, generated cmd/PowerShell shims, prefix disappearance/relink/unlink; direct Node guard | NOT TESTED for M2.2 |
| Native isolation | Two concurrent projects, real Node 20 vs 22 scripts, npm shims/adjacent Node, env/cwd/args/stdin/stdout/stderr/exit/signals; passthrough without config | NOT TESTED |
| Legacy migration and recovery | M1/M2/M2.1 bytes, modified launcher refusal, real interrupted routing/uninstall, external deinit/reinit and explicit rebind | NOT TESTED for new implementation |
| Full regression and wizard | Complete existing suite plus PTY/Windows console tests | NOT TESTED this stage; only focused baseline run |
| Windows/macOS/Linux CI | Passing new suite and native bootstrap build/provenance per supported runner | NOT TESTED; no new CI links |
| Windows ARM64 | Supplied artifacts do not prove execution | KNOWN LIMITATION |

Fixtures that fake `--version` are useful for resolver branches, but cannot prove
real Node compatibility. CI should obtain real versions through explicit job setup
outside Arch, with automatic manager downloads disabled during the tested command.
Record exact executable/version/runner and skip reasons. Test runtime probing and
concurrent launches without environment leakage. Real subprocess interruption tests
must remain in the complete matrix; do not replace them with filesystem mocks.

No acceptance criterion for the future implementation is declared complete here.
Stage B must produce its own implementation report and actual three-platform CI
links. This review recommends **CONDITIONAL GO**, contingent on explicit approval
of the two boundary changes and passing the feasibility gates above.

  and executable links; development links do not constitute an independent snapshot.

  global-package migration is version-installation-specific.

  it is not transparent runtime selection for the native process contract here.
- Local `vendor/README.md` identifies Scoop Shim cpp/v0.3.0 artifacts and hashes.
  Upstream source retrieval was unavailable during this review; advanced runtime
  lookup capability is **unverified**, not assumed from the binary's presence.

URL was unavailable in this review. Node 24 behavior claims above are confined to
the local executed 24.19.0 baseline and repository engine metadata. Stage B must
