# M2.2 B1 — runtime feasibility

Status: **B1 local executable evidence PASS; CONDITIONAL GO pending hosted CI and review.**
B2 is not authorized and has not been implemented. This is a feasibility checkpoint,
not a claim that M2.2 portability is available to users.

## Scope

Baseline: main `7944e8f`, plus accepted Stage A document commit `7e11f89`.
Branch: `feat/m2.2-b1-runtime-feasibility`.

Only production change: `src/process.ts` corrects Windows npm-script Node selection.
Simple Node `.cmd` shims use native PATH `node.exe`; standard npm shims with the
adjacent-Node branch prefer their adjacent `node.exe`. Missing native Node fails
with an explicit diagnostic instead of using `process.execPath` or `ARCH_NODE`.
Arguments, environment, cancellation and spawn APIs remain unchanged.

`scripts/b1/arch-bootstrap.cpp` is an **opt-in, Windows x64 feasibility prototype**.
It is not installed by npm, referenced by `renderFiles()`, or activated in projects.
Tests copy it into temporary app layouts and point temporary Scoop `.shim` files
at it. Those manually changed route fixtures are not presented as valid ownership
manifests; ownership/rebind tests use a separate, normally initialized project.

The prototype has one fixed application entry, adjacent `dist/cli.js`. It selects
an absolute `ARCH_NODE` override or the first `node.exe` on PATH, checks the package's
current range `>=24.15.0 <25` through a bounded version probe, and starts Arch with
inherited environment, cwd and standard handles. It rejects marked routers and
file-identity aliases to itself. An invalid override or incompatible first Node
does not trigger a search of other installations. No downloads, PATH writes,
manager discovery, new manifest metadata or generic launcher API were added.

Core, EDA/events, middleware, `setup.ts`, existing ownership/recovery journals,
manifest formats and npm bin entry remain unchanged. Old generated launchers still
capture Node/checkout paths; production integration belongs to B2 after review.

## Scoop reuse investigation

Inspected the exact source for vendored
[Scoop Shim cpp/v0.3.0](https://github.com/ScoopInstaller/Shim/blob/cpp/v0.3.0/cpp/shim.cpp).
`ExpandEnvVars` supports `%ARCH_NODE%`; `MakeProcess` uses `CreateProcessW` and
the shim supplies console handling and a job lifetime. There is no conditional
override/PATH policy or compatible-Node version check in that source.

Executed the vendored x64 binary with `path = %ARCH_NODE%` and a version-printing
script. It ran Node 24 successfully and **also ran Node 20 successfully**. This
proves useful expansion, but also proves that using Scoop alone would not enforce
the Arch engine contract. Its Windows implicit executable search also includes
locations outside PATH, unlike the proposed bounded runtime policy.

Decision: retain Scoop unchanged for route `.exe/.shim`; conditionally continue the
small fixed-entry bootstrap, subject to hosted executable evidence and review.
Do not extend/fork Scoop into a general runtime launcher.

### Failures encountered and resolved

- Sandbox blocked Node 20's `lstat` of the user-home ancestor. Re-running the real
  runtime checks outside the sandbox passed; no production ownership or filesystem
  check was weakened.
- Windows file symlink creation required privileges. The fixture now tests a hard
  link and directory junction without requiring file-symlink privilege.
- One malformed-probe assertion expected the compatibility diagnostic instead of
  the earlier output-bound diagnostic. Corrected the assertion; both reject before
  harness dispatch. The stalled executable check then passed.
- The extracted standalone PTY fixture initially inherited both `Path` and `PATH`.
  Normalizing that test fixture fixed native resolution. Production inherits the
  environment without constructing a competing PATH entry.
- node-pty 1.1 retained worker handles after successful exit. Following the existing
  wizard checker, the standalone runner now awaits child exit and scratch cleanup,
  flushes output and explicitly exits. Killing an already exited terminal had
  produced an `AttachConsole` helper error; that unnecessary kill was removed.
- First hosted Windows runs found short/long temporary-path assertion mismatches
  (`RUNNER~1` versus `runneradmin`). New fixtures now canonicalize the temporary
  root before creation, as the existing wizard checker does. No production path
  or ownership logic changed to accommodate these assertions. Initial failing
  runs: [B1](https://github.com/Nickshajtan/hcc-harness/actions/runs/40801339888),
  [regressions](https://github.com/Nickshajtan/hcc-harness/actions/runs/40801339851).

## Standard npm installation vs custom snapshot (B2 design adjustment)

Prefer investigating **standard npm installation into an explicit stable prefix**:
`npm pack`, followed by `npm install --global --prefix <stable-directory> <local-tarball>`.
No global npm configuration/profile/PATH rewrite is needed; bin links and dependency
installation stay npm's responsibility. A local tarball avoids the development
checkout link created by `npm link`/some directory-install modes. `private: true`
and no registry publishing remain requirements.

Executed **pack dry-run only**, with an isolated cache: current metadata includes
all built `dist/*` and vendor shims. No tarball installation, stable prefix, upgrade
or removal was implemented or tested. Dependency installation/offline reproducibility,
supported npm versions, executable placement and runtime-independent management
entry still need B2 evidence. npm's ordinary Node-script shims alone cannot select
an independent Node when ambient Node is missing/incompatible.

Compared with a custom file-copy installer, standard npm owns fewer new lifecycle
rules and follows the existing bin contract. There is currently **no demonstrated
need for a custom snapshot installer**. The Stage A design records this adjustment;
its original custom-copy proposal is superseded as the preferred candidate.
References: [npm install](https://docs.npmjs.com/cli/v11/commands/npm-install/),
[npm pack](https://docs.npmjs.com/cli/v11/commands/npm-pack/),
[npm folders](https://docs.npmjs.com/cli/v11/configuring-npm/folders/).

## Remaining risks and boundaries

- Prototype version-range logic is deliberately fixed to current package engines;
  production integration must prevent metadata drift and add a CLI guard before
  harness imports. Direct Node/npm-bin invocation has not gained that guard in B1.
- Windows PATH runtime resolution supports `node.exe`, including ordinary executable
  links. Arbitrary `.cmd`/PowerShell runtime wrappers and every version manager are
  not proved; there is no automatic discovery of their installations.
- Native npm handling preserves the existing supported Node-script shim subset;
  it is not a batch interpreter or full emulation of customized npm wrappers.
- Console checks retain the existing Windows allowed result set (130/149 or
  `0xC000013A`), require cleanup, and check for no native survivor. They do not
  establish every terminal emulator's behavior or force-kill cleanup semantics.
- Static CRT, job nesting, trusted PATH and version probing need supported-runner
  evidence. A version probe is not attestation of an untrusted executable.
- Temporary app copies link repository dependencies for feasibility; they do not
  prove a self-contained stable installation or source-checkout deletion behavior.
- No old launcher is silently rewritten. Missing historical target recovery remains
  ownership-based; existing journal/collision tests remain regression gates.
